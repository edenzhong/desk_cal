# 技术选型文档

## 概述
本文档描述 macOS 桌面日历应用的技术栈选择，包括编程语言、框架、库和工具。根据最新决策，采用**动态墙纸方案**：通过生成日历图片并设置为系统墙纸来实现桌面日历功能。

## 方案对比：动态墙纸 vs 桌面窗口
| 维度 | 动态墙纸方案 | 桌面窗口方案 |
|------|--------------|--------------|
| **实现复杂度** | 简单：图片生成 + 墙纸设置 API | 复杂：窗口层级管理 + 事件监听 |
| **资源占用** | 极低：仅定时任务运行 | 较高：常驻窗口 + 事件监听 |
| **系统集成** | 高：使用标准墙纸 API | 中等：需要特殊窗口层级 |
| **用户体验** | 日历持续显示 | 仅显示桌面时出现 |
| **多显示器** | 简单：系统原生支持 | 复杂：需要自定义处理 |
| **技术风险** | 低：成熟 API | 中等：窗口层级可能变化 |
| **权限需求** | 无需特殊权限 | 可能需要辅助功能权限 |

## 核心需求对应的技术挑战
1. **图片生成**：需要高效生成高分辨率、美观的日历图片
2. **全年日历布局**：需要计算日期并生成12个月的网格布局
3. **墙纸设置**：需要将图片设置为 macOS 桌面墙纸
4. **定时更新**：需要每天自动更新墙纸，确保日期准确
5. **多显示器适配**：需要支持不同分辨率和 DPI（Retina 显示）
6. **界面美观**：需要生成与系统日历风格协调的图片

## 技术选型

### 编程语言：Swift
- **理由**：macOS 原生开发首选语言，与 Cocoa 框架深度集成，性能优越，内存安全
- **备选方案**：Objective-C（较旧）、Python + 脚本（需要打包）
- **选择原因**：Swift 是苹果官方推荐语言，与系统 API 集成好，适合生成图片和调用墙纸 API

### 图片生成框架
- **Core Graphics (Quartz 2D)**：底层绘图框架，精细控制，性能高
  - 优点：完全控制每个绘图操作，支持 Retina 分辨率，轻量级
  - 缺点：命令式 API，代码量较大
- **SwiftUI + ImageRenderer**：声明式 UI 转图片（macOS 12+）
  - 优点：使用 SwiftUI 语法，开发效率高，易于维护
  - 缺点：需要 macOS 12+，性能可能略低于 Core Graphics
- **选择**：**Core Graphics** 为主，确保兼容 macOS 11.0+ 和最佳性能

### 日历计算
- **Foundation.Calendar**：提供日期计算、月份天数、星期几等核心功能
- **Foundation.DateComponents**：用于构建和解析日期
- **优势**：系统内置，无需第三方库，处理时区、本地化等复杂情况

### 墙纸设置 API
- **NSWorkspace**：`setDesktopImageURL(_:for:options:)` 方法
- **屏幕识别**：`NSScreen.main` 获取主显示器，`NSScreen.screens` 获取所有显示器
- **墙纸选项**：支持填充、适应、拉伸等模式，保持用户现有设置

### 定时任务管理
- **Timer**：应用内定时器，每天触发更新
  - 优点：简单易用，无需外部依赖
  - 缺点：应用需常驻内存
- **launchd**：系统级定时任务
  - 优点：应用无需常驻，资源占用极低
  - 缺点：配置复杂，需要安装 plist 文件
- **选择**：**Timer** 方案，简化部署，确保可靠执行

### 多显示器处理
- **NSScreen**：获取所有显示器的分辨率、DPI、唯一标识
- **独立生成**：为每个显示器生成适合其分辨率的图片
- **系统设置**：使用 NSWorkspace 为每个屏幕设置墙纸
- **主显示器优先**：初始版本可先支持主显示器，扩展为可选功能

### 项目结构和构建工具
- **Swift Package Manager (SPM)**：主要构建工具，用于项目创建、依赖管理、编译构建
- **Swift 编译器 (swiftc)**：命令行编译工具，用于直接编译 Swift 代码
- **项目结构**：
  - 使用 SPM 创建可执行包（`swift package init --type executable`）
  - 纯命令行工具，后台运行，可配置为登录项自动启动
  - 无图形界面依赖，通过命令行参数和配置文件进行控制
  - 可选：通过系统 API 创建简单的菜单栏控制项（需要额外开发）

| SwiftLunar | ⭐⭐⭐⭐ | 另一个Swift农历库，功能类似 |

- 轻量级，适合命令行工具集成

### 假期API技术选型
| 方案 | 推荐度 | 说明 |
|------|--------|------|
| **timor.tech** | ⭐⭐⭐⭐⭐ | 免费公开API，返回JSON数据，无需认证 |
| 节假日数据API | ⭐⭐⭐⭐ | 另一个免费的节假日API |
| 硬编码假期数据 | ⭐⭐ | 需要手动维护，灵活性差 |

**推荐方案**：使用 [timor.tech](https://timor.tech/api/holiday)

**API信息**：
- 基础URL：`https://timor.tech/api/holiday`
- 接口示例：
  - `GET /holiday/{year}/{month}/{day}` - 查询某天是否为节假日
  - `GET /holiday/{year}/{month}` - 查询某月的节假日
  - `GET /holiday/{year}` - 查询某年的节假日
- 返回数据格式：
```json
{
  "code": 0,
  "holiday": {
    "holiday": true,
    "name": "春节",
    "wage": 3,
    "date": "2026-02-17"
  }
}
```

## 技术决策理由

### 为什么可以在无 Xcode IDE 环境下开发？
1. **技术栈匹配**：动态墙纸方案使用 Core Graphics 和系统 API，不依赖 SwiftUI 预览或界面构建器
2. **命令行工具完备**：Swift 编译器、Swift Package Manager、Xcode 命令行工具已提供完整开发能力
3. **轻量级开发**：Core Graphics 是底层框架，代码编写和调试可通过日志和命令行完成
4. **部署简化**：生成的可执行文件可直接运行，无需复杂的应用打包流程
5. **资源友好**：避免安装 10GB+ 的 Xcode IDE，适合存储空间有限的开发环境

### 为什么选择动态墙纸方案而非桌面窗口？
1. **简化实现**：图片生成 + 墙纸设置 API 比窗口层级管理 + 事件监听更简单
2. **资源效率**：无常驻窗口，仅定时任务，系统资源占用极低
3. **系统集成**：使用标准墙纸 API，兼容性更好，技术风险更低
4. **用户体验**：日历作为墙纸持续显示，符合"桌面日历"的直观认知
5. **多显示器**：系统原生支持多显示器墙纸设置，实现更简单

### 为什么选择 Core Graphics 而非 SwiftUI ImageRenderer？
1. **兼容性**：Core Graphics 支持 macOS 11.0+，ImageRenderer 需要 macOS 12+
2. **性能控制**：Core Graphics 提供精细的绘图控制，适合批量生成高分辨率图片
3. **轻量级**：无需启动 SwiftUI 渲染引擎，资源占用更低
4. **稳定性**：Core Graphics 是成熟的底层框架，行为可预测

### 为什么选择 Timer 而非 launchd？
1. **部署简单**：Timer 集成在应用中，无需系统级配置
2. **调试方便**：应用内定时器更容易调试和监控
3. **可靠性**：避免 launchd 配置错误导致任务不执行
4. **用户控制**：应用常驻可提供菜单栏控制界面（可选）

## 开发环境要求
- **开发 macOS**：11.0 (Big Sur) 或更高（支持 Swift 6.0+）
- **必需组件**：Xcode 命令行工具（包含 Swift 编译器、Swift Package Manager）
- **开发工具**：文本编辑器（如 VS Code、Sublime Text、Vim 等）+ 命令行工具
- **部署目标**：macOS 11.0（兼容 Intel 和 Apple Silicon）
- **存储要求**：无需安装完整 Xcode IDE（节省 ~10GB 存储空间）

## 风险与缓解
| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| 图片生成性能问题 | 中 | 中 | 优化绘图代码，缓存生成结果，仅在日期变更时重新生成 |
| 墙纸设置失败 | 低 | 高 | 检查文件权限，使用临时文件，提供错误恢复机制 |
| 用户手动更改墙纸 | 中 | 中 | 可选：检测墙纸变化并恢复，或提供用户控制选项 |
| 多显示器适配复杂 | 中 | 中 | 初始版本仅支持主显示器，后续逐步扩展 |
| 定时任务不执行 | 低 | 中 | 使用可靠的 Timer 实现，添加日志记录，提供手动更新选项 |
| 高 DPI (Retina) 支持 | 低 | 高 | 使用 Core Graphics 的 scale factor 支持，测试不同显示器 |

## 结论
采用 Swift + Core Graphics 方案，通过生成日历图片并设置为系统墙纸实现桌面日历功能。该方案简化了实现复杂度，降低了资源占用，利用成熟的 macOS 墙纸 API 提供稳定的用户体验。动态墙纸方案在简洁性、资源效率和系统集成方面优于桌面窗口方案，是满足项目需求的最佳选择。
